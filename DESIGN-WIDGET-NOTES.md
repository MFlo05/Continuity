# Per-Widget Visual Notes

> **Reference material, not briefing material.** Read the entry for the widget
> or surface you're actually changing — this file is not meant to be read
> linearly, and nothing in it applies app-wide.
>
> Each entry records what that widget's appearance is *meant* to be and, where
> relevant, decisions that were deliberately made and **shouldn't be "fixed"**
> by a future pass. A surprising number of these are the second or third
> attempt at the same problem; the reasoning is the point, not the value.
>
> The app-wide rules these entries sit on top of — colour tokens, the tone +
> wash system, typography, iconography, "what NOT to do" — live in
> **`DESIGN_SYSTEM.md`**. Implementation traps (Obsidian's button/SVG
> overrides, the `!important` cascade, portal token bridges) live in
> **`UI-PATTERNS.md`**.

## Recipe Vault Widget (REMOVED) + full-screen view

**`RecipeVaultWidget.tsx` (the original plain-list browser) was deleted outright** once `RecipeBoxWidget` (below) proved out — the user tried it, preferred it, and asked to fully remove the old one rather than keep it as a fallback option. `'recipe-vault'` is gone from `WidgetType`/`widgetRegistry`; anyone with that widget type already placed on their dashboard will need to remove/replace it manually (no migration was added — not worth the complexity for a pre-1.0 personal plugin). `cc2-rv-*` classes weren't deleted along with the widget — `RecipeBoxWidget`'s "Add with AI"/"+" toolbar buttons literally reuse `.cc2-rv-ai-add`/`.cc2-rv-add` by class name (identical buttons, no reason to fork the CSS), while its search/category row has its own `.cc2-rb-search`/`.cc2-rb-category` classes with matching (not shared) values, since those needed independent geometry for the compact card-stack layout. `cc2-recipe-fs-*` for the full-screen reading view remains fully in use (by both `RecipeBoxWidget` and `MealPlannerWidget`) and is untouched by the removal.

`src/data-sources/recipes.ts` is deliberately modeled on `meetings.ts` — template folder (`Templates/Recipes/`), `cc2-extra-fields` directive, `{{placeholder}}` substitution, filename-as-title — right down to duplicating `parseFrontmatter`/`serializeFrontmatter`/etc. rather than importing them from `meetings.ts`. This is the same accepted tradeoff `meetings.ts` itself documents (narrow parser scoped per-file, not a shared module) — now exercised a second time. If a third data source needs this exact shape, that's the point to actually extract it; two instances isn't there yet. One addition beyond meetings.ts: ingredients live in a `## Ingredients` section as `- [ ] qty unit name` checkbox lines (same shape/format as Grocery List, via the shared `parseIngredientLine`), extracted with a section-scoped parser (`findSectionRange`, mirroring `todos.ts`'s bucket-scoped `findBucketRange`) rather than treated as more free-text body content — this is what makes the full-screen ingredient checklist (and, later, "add to grocery list") possible.

**`RecipeFullscreen.tsx` is the first thing in this plugin to use Obsidian's real `MarkdownRenderer`.** Everything else that shows note content either redirects to the real editor (`openLinkText`) or displays plain extracted text/frontmatter fields — this is the first "render actual markdown formatting inside a custom widget" case. `MarkdownRenderer.render(app, markdown, el, sourcePath, component)` is imperative (it appends DOM into an element you own), so it's wrapped in a small `MarkdownBlock` component: a ref + `useEffect` that calls `el.empty()`, creates a throwaway `new Component()` to `load()`/pass to the renderer/`unload()` on cleanup (that's what tears down embedded child components on re-render or unmount), matching how Obsidian's own views manage renderer lifecycles. The full-screen view renders ingredients as its own interactive checklist (not through the markdown renderer — clicking a row needs to call `toggleIngredient`, which raw-rendered markdown checkboxes can't be wired to) and strips the `## Ingredients` section out of what it hands to `MarkdownBlock` (`stripIngredientsSection`) so it isn't shown twice.

Portal/token-bridge: `.cc2-recipe-fs-backdrop` was added directly into the *existing* `.cc2-cal-fs-backdrop`/`.cc2-cal-modal-overlay` token-bridge selector (both light and dark blocks) rather than declaring a third copy of the same `--cc2-*` variable list — same values, no reason to fork them. Any future full-screen/stage-level portal should extend that selector list too, not copy-paste the block again.

**Wired into the per-widget tone system, Trim only — no Wash, and its settings live on Recipe Box, not here.** There's no independent Widget Settings entry for `RecipeFullscreen` itself; `RecipeBoxWidget` (below) is the only thing that opens it, so `tone`/`wash` are read once from `RecipeBoxWidget`'s own `config` and passed straight down as props (`<RecipeFullscreen tone={tone} wash={wash} />`), the same "compact widget owns the settings, fullscreen just inherits them" relationship Calendar already established. Wash is deliberately never applied here (`RecipeBoxWidget.tsx`'s `showWash={false}` on its `TonePicker` call hides the toggle entirely at the source, so there's no wash value to even forward) — elements following `--t` instead: the category chip row (`.cc2-recipe-fs-chip` — background/border/text all switch from flat `--cc2-bg`/`--cc2-border`/`--cc2-muted` to `--t-bg`/`--t-line`/`--t`, a real per-chip tint rather than a page-level wash), the ingredient quantity text (`.cc2-recipe-fs-ing-qty`), and the checked-ingredient checkbox fill (`.cc2-recipe-fs-ing-check` in its `.done` state). The checkbox is a deliberate, explicit divergence from the shared "done/checked green" convention (`#5F9E6E`, see Meal Planner's category-color-bar note) — written as `var(--t, #5F9E6E)` so it falls back to the exact same green everyone else sees until a tone is actively chosen for this specific widget.

**Categories vs. tags — two different mechanisms, on purpose.** Tags stay freeform (typed into a `cc2-extra-fields`-declared text input, comma-separated). Categories are a *fixed* vocabulary (`RECIPE_CATEGORIES` in `recipes.ts` — Appetizers, Soups, Salads, Main Dishes, Sides, Dessert, Breads, Eggs, Vegetables, Pasta, Brunch, Cocktails, Breakfast) with dedicated UI: a multiselect chip row (reusing `.cc2-flush-btn.active`) in the create modal, always present regardless of which template is selected, and a single-select native `<select>` filter dropdown beside the widget's search box. Both still land in frontmatter as a comma string (`categories: Breakfast, Brunch`), parsed by the same `parseCommaList` helper tags use — the only difference is *how the value gets typed in*, not how it's stored. Don't route a fixed-vocabulary field through `cc2-extra-fields` (a plain `<input type="text">`) — build it as a real widget-level feature like this one, the same way Categories replaced an earlier attempt to just add it as another extra-field.

**Ingredient lines can carry embedded markdown links** (`- [ ] 1 cup [milk](https://amzn.to/...)` — common when pasting from recipe sites). `parseIngredientLine` (`ingredient-line.ts`) strips well-formed `[text](url)` pairs down to `text` for the parsed `name` (so search/filter/scaling see clean ingredient names, not link syntax) while capturing the first URL separately as `url`. The stored `raw` field is untouched (original markdown intact) — that's what `toggleIngredient`'s regex match/replace needs to find the real line in the file, so don't "clean up" `raw` anywhere. `RecipeFullscreen` renders `name` as a real clickable `<a>` when `url` is present (shopping links are genuinely useful to keep); Grocery List ignores `url` entirely and just shows plain text. A malformed/truncated link (stray `[` with no closing `]`/`(...)`) is left as literal text rather than partially "fixed" — not this parser's job to repair bad paste artifacts.

**Ingredient parsing is a small tokenizer (quantity token → unit token → remainder is the name), not one mega-regex.** `ingredient-line.ts`'s original single-regex version had two real bugs, found by testing against a real pasted recipe: no support for mixed numbers (`1 1/2 cups`) or attached Unicode fraction glyphs (`1½ cups`), and unanchored short unit abbreviations partial-matching inside unrelated words (`4 Large eggs` → unit `l`, name `arge eggs`, since the bare `l` alternative had no word-boundary). Fix: `parseLeadingQuantity` tries mixed-number → simple-fraction → digit+attached-Unicode-fraction → bare-Unicode-fraction → plain decimal, in that order (most-specific first, so `1 1/2` doesn't get truncated to just `1`); `matchLeadingUnit` matches against a `UNIT_TABLE` (canonical key → full-word + abbreviation aliases) with `\b...\b` word-boundary anchoring, which alone fixes the "Large" bug (the position right after a lone `l` in "Large" sits between two word characters, so `\b` fails there and the regex backtracks to the next alias instead of accepting a bad partial match). `qty` is a real `number | null` now (not a display string) so it can be scaled — `formatQty()` is the display-side counterpart, snapping any value to the nearest of `{1/2, 1/3, 1/4, 1/6, 1/8}` rather than ever printing a raw decimal, since cooking measurement tools don't support arbitrary decimals anyway. Canonical units are always singular in display (`"cup"`, not `"cups"`) even when the quantity is plural — a known, accepted cosmetic simplification, not a bug.

**Ingredient checkboxes in the full-screen view are session-only, never written to the file.** They used to call `toggleIngredient` (now deleted from `recipes.ts`) to flip the actual `- [ ]`/`- [x]` line in the note — but that meant the *next* time you cooked the same recipe, every box was still checked from last time and had to be manually cleared first. Fixed by tracking checked state in a plain local `Set<string>` (`checkedSet`, keyed by each ingredient's raw line text) that starts empty on mount and is never persisted — closing the full-screen view (which unmounts the component) is what resets it, no timer/expiry logic needed. If a longer-lived "survive an accidental close mid-cooking" version is ever wanted, that's new, deliberate scope, not an oversight in this one.

**`createRecipeNote` always writes every declared meta field to frontmatter, even blank.** Previously a field the user left empty in the create modal (e.g. `sourceUrl`) was skipped entirely — meaning adding it later meant typing the property name from scratch in Obsidian's Properties UI instead of just filling in a value. Now every `cc2-extra-fields`-declared key (and `categories`) always lands in frontmatter, empty string if unfilled.

**Calling `newConversation()` immediately before `sendMessage()` in the same handler doesn't reliably target the new conversation — found via this exact bug in "Add with AI".** Both are plain functions defined inside `AIProvider`'s render, closing over that render's `activeConvId`/`conversations` state. `setActiveConvId(id)` inside `newConversation()` only *schedules* a re-render; it doesn't update the `sendMessage` closure the caller is about to invoke in the same synchronous tick, so `sendMessage` read the *old* `activeConvId` and silently sent into whatever conversation was previously active — while the panel UI (which does pick up the eventual re-render) showed the new, empty one. Symptom: "the AI panel opens to a new chat, but the response happens somewhere else." Fixed by giving `sendMessage` its own `opts.forceNewConversation` (`SendMessageOpts` in `AIContext.tsx`) that reuses its existing (already-correct) auto-create-if-no-active-conversation branch atomically, instead of two separate state updates racing each other. **Any future caller that wants "start fresh and send" needs `sendMessage(text, files, images, { forceNewConversation: true })` — never `newConversation()` followed by `sendMessage()`.**

**Scoping `claudeYoloMode` to a single call** (also in "Add with AI"): flip it via `updateSettings({ claudeYoloMode: true })`, `await` the `sendMessage(...)` call, then flip it back to whatever it was in a `finally`. This works because `sendMessage`'s returned promise only resolves once the spawned CLI process for that turn actually exits (`claude-cli.ts`'s "one cold-start process per message" model) — so the window is genuinely just that one turn, not "until the user remembers to turn it back off." Don't flip `claudeYoloMode` for a call whose completion isn't awaited this way; it'll leak into whatever the user does next in the panel.

**`claude-cli.ts`'s `child.stdin.end()` timing is load-bearing in both directions — got this wrong twice before landing on the right spot.** First cut: called it right after writing the initial message. In Safe mode (`yolo: false`), the CLI can send a `can_use_tool` control_request asking for permission at any point after that first write and blocks waiting for a `control_response` on that same stdin — ending stdin that early closes the pipe before any tool actually needs approval, so the first real tool-permission round-trip fails with "Stream closed." Fix attempt #1 was to just never call `.end()` — that broke the *other* direction: the CLI's own main loop apparently stays parked waiting for either another stdin line or EOF even after it's fully generated a turn's response, so with stdin never closed, a turn with **no** pending permission prompt (e.g. a YOLO-mode turn, which never sends `can_use_tool` at all) would finish and then hang forever — `child.on('exit')` never fires, the wrapping promise never settles, and the AI panel's `streaming` flag stays stuck `true` (composer/send button dead) until Obsidian is reloaded. The actual fix: end stdin exactly once, triggered by the CLI's own `result` message (success or error) arriving on stdout — that message only ever shows up after every tool call and control_request/control_response round-trip for the turn has already resolved, so it's the one signal that's simultaneously "safe to close" and "necessary to close." Don't special-case this per yolo mode; the same `result`-triggered close is correct for both.

**External links (a real `https://` URL the user should open in their actual browser) need `window.open(url)`, not a plain `<a href target="_blank">`.** The native anchor `target="_blank"` didn't reliably work from custom React-rendered links in Obsidian's Electron shell — both the ingredient shopping links and the recipe's "View original recipe" link were dead until switched to `onClick={e => { e.preventDefault(); window.open(url); }}`, matching the pattern already proven working in `google-oauth.ts` (`window.open(url)` to launch the OAuth consent page in the system browser). Keep the `href` attribute for right-click "copy link" / hover-preview, but always drive the actual navigation through `window.open`, never bare `target="_blank"`.

**Tags stay freeform and unbounded; categories stay a fixed, curated vocabulary — and only categories get a chip/dropdown filter UI.** Recipe Vault originally rendered every distinct tag across all recipes as a clickable filter chip, the same treatment categories get. That works for categories (13 fixed values, never grows) but not for tags — AI-imported recipes generate a new freeform tag or three per recipe, so the chip row would grow unbounded and turn into visual noise within a few dozen recipes. Fixed by dropping the tag-chip row entirely: tags are still shown per-row and still searchable (the search box now matches against `tags` as well as `title`), just never promoted to their own permanent filter UI. If a *fixed*-vocabulary metadata field is added to recipes in the future, it should get the categories treatment (dropdown/chips); an open-ended, AI-generated field should not.

**"Add with AI" (`RecipeVaultWidget.tsx` toolbar + `RecipeImportModal.tsx`) is the first widget outside the AI panel itself to call `useAI()`.** Gated on `settings.activeProvider === 'claude' && settings.claudeAuthMode === 'cli'` — the only mode with real fetch/tool capability (see `src/ai/AIContext.tsx`'s `AISettings`); disabled otherwise with a tooltip naming the current provider, using `.cc2-flush-btn:disabled`'s existing dim treatment rather than hiding the button. Shows the active provider's real logo via the existing `<BrandMark provider={...} size={...} isDark={...}>` (`src/ai/BrandMark.tsx`) + `useIsDark()` (`src/ai/AIPanel.tsx`) — reused as-is, not re-derived. On submit: `newConversation()` (so the import prompt can't land in an unrelated, possibly wrong-provider conversation) → `setPanelOpen(true)` → `sendMessage(...)`, then the import modal closes immediately — the plugin doesn't drive anything further. Claude writes the actual `.md` file directly with its own tools per `00-System/Skills/Recipe-Creation.md` (a vault file, not part of this repo — kept token-lean since it's read into context on every invocation: compact bullet spec, no narrative prose, matches the house style of the user's other `00-System/Skills/*.md` files). `RecipeVaultWidget`'s existing `watchRecipesFolder` file-watcher is what picks up the new note once Claude finishes — no callback/promise plumbing back into this plugin.

**Recipe serving scaling (`RecipeFullscreen.tsx`) is view-only/ephemeral, on purpose.** `currentServings` is local React state, reset to the note's real `servings` frontmatter value every time a different file loads — changing it in the UI recomputes every ingredient's *displayed* quantity (`formatQty(ing.qty * (currentServings / baseServings))`) but never writes back to the file. If a "save this scaled version" feature is ever wanted, that's new, deliberate scope — don't assume scaling should persist.

**The `## Image` section is rendered through `MarkdownBlock`, not a plain `<img src>`.** Obsidian embeds (`![[Pasted image ....png]]`) are wikilink syntax, not a resolvable URL — only Obsidian's own renderer knows how to turn that into a real attachment path. `parseRecipeNote` (renamed from `splitRecipeBody` once it grew to also return `meta` — see above) extracts the section's raw text as one or more embed lines (multiple `![[...]]` lines become gallery slides, split in `RecipeFullscreen` into a `photos` array) and hands each active slide to the same `MarkdownBlock` component used for the rest of the note. Lives in `.cc2-recipe-fs-gallery` in the right-hand `.cc2-recipe-fs-side-col`, below the info card, as part of the 60/40 `.cc2-recipe-fs-layout` (`grid-template-columns: 3fr 2fr`, `@media` stack below 760px). The gallery frame fills all remaining height in that column (`flex: 1 1 0`) with the image `object-fit: cover; object-position: center` so it always fills the frame without letterboxing, cropping from the center rather than losing the focal point; position among multiple photos is shown only via the "N / total" counter overlay (no separate dot indicators — removed as redundant).

## Meal Planner Widget (`cc2-mp-*` + `cc2-mp-box-*`)

Rebuilt from a Claude-Design handoff (`design_handoff_meal_planner/`, deleted after the port per the user's own instruction — read it early if you're chasing an exact pixel value that seems to have no rationale in this doc). Week-plan file model, `MealBlock`/`fitsPlan`, and week math are unchanged from the original build (see `meal-plan.ts`) — this rewrite replaced the *widget* (`MealPlannerWidget.tsx`) and the recipe-picker (`RecipeBoxModal.tsx`, new file, replacing the old floating drawer) wholesale, plus a new `colSpan`-per-`MealBlock` data model (a block now spans multiple day-columns instead of every duplicate being its own single-cell entry).

**Pointer-events drag, not native HTML5 DnD — a deliberate break from Kanban's precedent, because this design needs things `dataTransfer` can't model:** stretch-resize (dragging a card's right edge to grow its day-span) and click-to-place duplicate (arm on click, place on the *next* click anywhere, not a held drag) don't fit the native drag API at all. Every gesture (move, stretch, duplicate-placement, and "new" placement dragged out of the Recipe Box) follows the same shape: a `pointerdown` handler that adds its own `onMove`/`onUp` closures straight to `window` and removes that *exact same pair* on release — not `useCallback`-stabilized handlers reused across renders. This avoids any stale-closure risk entirely (each gesture's closures capture that gesture's starting values fresh) at the cost of re-declaring the same add/remove boilerplate four times (`startDrag`, `handleBodyDown`, `handleStretchDown`, `startPlacing` in `MealPlannerWidget.tsx`) — accepted, since trying to unify them behind one generic "pointer gesture" abstraction would obscure what's actually a fairly small amount of per-gesture logic.

**Stretch is live-previewed locally, never streamed to the vault.** `handleStretchDown`'s `onMove` only calls `setLiveStretch({day,row,colSpan})` (plain React state, re-rendered instantly); the real `stretchMeal()` vault write happens exactly once, in `onUp`. `effectiveBlocks` (a `useMemo` over `blocks` + `liveStretch`) is what actually renders — writing on every `pointermove` would mean a `vault.process` call per pixel of cursor movement, both slow and needless since only the final value matters.

**Body-drag vs. click-to-open uses a 5px movement threshold** (`handleBodyDown`): pointerdown arms a listener pair that only calls `startDrag(...)` once the cursor has moved more than 5px, otherwise pointerup with no movement opens `RecipeFullscreen` directly. Hover-only controls (duplicate ⧉, remove ×, the stretch handle) all carry `data-nodrag="1"`, which `handleBodyDown` checks via `closest()` before arming — clicking a control never starts a body-drag.

**Hit-testing is `document.elementFromPoint(x,y).closest('[data-daycell="1"]')`**, reading `data-day`/`data-row` off whatever it finds — this is why the Recipe Box modal has to visually *collapse* (`.cc2-mp-box-backdrop.collapsed`: transparent, `backdrop-filter:none`, `pointer-events:none`) the instant a "new" drag starts (`drag?.type === 'new'`, exposed to `RecipeBoxModal` as its `collapsed` prop): with `pointer-events:none` on the backdrop, `elementFromPoint` skips straight through it to the actual grid cell underneath. Without that, every drag-from-the-box would hit-test against the modal's own backdrop instead of the grid, no matter how the z-index was tuned.

**The floating ghost + "Drop on a planner slot ↓" hint are portaled to `document.body` but deliberately skip the `--cc2-*` token bridge** — they lean on Obsidian's own always-global vars (`--background-primary`, `--text-normal`, `--interactive-accent`) instead. Every other portaled surface in this plugin (`.cc2-modal-backdrop`, `.cc2-recipe-fs-backdrop`, and the new `.cc2-mp-box-backdrop`) declares a full light/dark `--cc2-*` bridge because it's a whole panel using a dozen+ of those variables; the ghost/hint are two small elements needing at most three colors, and they aren't DOM descendants of anything that already carries the bridge (they're siblings of `RecipeBoxModal`'s own portal, not nested inside it) — so reaching for Obsidian's own globals was simpler than inventing a bridge just for them.

**Recipe Box (`RecipeBoxModal.tsx`) reads real vault data via `loadRecipeCardData` (`recipes.ts`)**, not the design's hardcoded four-recipe array — `listRecipeEntries` for the file list, then `Promise.all(...loadRecipeCardData)` for full per-card data (image URL, ingredient count, servings/prep/cook/total minutes) up front when the modal opens. Search matches title or tags; the category `<select>` filters by the fixed `RECIPE_CATEGORIES` vocabulary (same dropdown Recipe Vault uses) — both reset the scroll stack to the top.

**The scroll-driven "peel stack" is ported verbatim from the design's own math** (`PEEK=15, SCALE_STEP=0.055, CAP=3, FRONT=CAP*PEEK`; `peelFor(i,k)` in `RecipeBoxModal.tsx` mirrors the prototype's `_onStackScroll` branches exactly: `eff<=-1` fully gone, `-1<eff<0` the front card peeling off (`ty=FRONT+peel*400`, opacity cuts out past `peel>0.82`), `eff>=0` the resting fan (`ty=FRONT-d*PEEK`, `scale=1-d*SCALE_STEP`, capped at depth 3). Two things differ from a literal port: (1) `onScroll` **mutates each mounted card's `style.transform` directly via refs**, not through `setState` per scroll tick — only `stackFront` (which ~7 cards are mounted, `front-1..front+5`) goes through React state, and only when it crosses an integer boundary; this matches the design's own intent ("no CSS transition on the peel transform… tracks the scrollbar 1:1") more literally than a React-state-per-tick version would, since direct DOM mutation has zero reconciliation latency. (2) It's a native `onScroll` prop on the stack `<div>`, not the prototype's manual `addEventListener` in `componentDidUpdate` — React's synthetic scroll handling covers the same case with less code.

**Card flip (`.cc2-mp-box-flip`) keeps the design's redundant fallback**: `backface-visibility:hidden` *and* a same-class `opacity` toggle with `transition: opacity 0s linear 0.275s` (half of the 0.55s flip) on each face, per the design's own note that `backface-visibility` alone is unreliable across engines. Don't remove one leg of this thinking it's dead code.

**Deliberate deviations from the design handoff — flagged per the standing rule to call these out rather than silently diverge:**
- **Font**: Newsreader (already loaded for `RecipeFullscreen`'s title, now expanded to weights 600/700) stands in for the design's specified Spectral, for consistency with the existing recipe UI rather than loading a second serif family. Body/UI text stays on the inherited `--font-interface`, not the design's Hanken Grotesk.
- **No separate light/dark toggle**: the design's own theme-toggle button (☾/☀) was omitted — Obsidian's theme already drives every `--cc2-*` value plugin-wide; a second, widget-local toggle would be redundant and is a pattern no other `cc2-*` widget has.
- **Category-color bar → fixed green**: the design colors the meal-block's left stripe (and the Recipe Box's "Drag to plan" pill) per-category (`CAT_COLORS`). Per explicit user request, both are hardcoded to `#5F9E6E` instead — the same green `RecipeFullscreen`'s checked-ingredient checkboxes use — "for continuity" between the two widgets, overriding the design's own category-color system entirely (no `CAT_COLORS`-equivalent exists in the ported code at all).
- **Toolbar title / "THIS WEEK" badge / "+" glyph**: per explicit user request, the toolbar title uses the plugin's own `.cc2-*-title` convention (13px/700 UI font) rather than the design's Spectral 20px/600, and the "THIS WEEK" badge + the "+" in "+ Recipes" use `var(--cc2-accent)` (Obsidian's real `--interactive-accent`) rather than the design's separate configurable accent color.
- **Grid metrics scaled down slightly**: 94px label gutter / `minmax(74px,1fr)` rows in the spec became 76px / `minmax(58px,1fr)` here, since this is a resizable GridStack widget (min size `{w:8,h:3}`) rather than a fixed-width standalone page — colors, radii, and type sizes otherwise match the spec exactly.

**`Full recipe →` and clicking a placed meal both open the plugin's real `RecipeFullscreen`** — never the design's own full-screen mockup, which was reference-only and not ported. `RecipeBoxModal` takes an `onOpenFullscreen(file: TFile)` callback for this; `MealPlannerWidget` owns the single `openFile` state both the grid and the box modal write into.

**Both "Drag to plan" pills (front and back card faces) — and "Full recipe →" — must close the Recipe Box the instant they're pressed, not on drop/wait.** `RecipeBoxModal` is a centered modal; leaving it open (even visually "collapsed") still blocks the grid the user needs to see to aim a drop. Fixed by calling `setShowBox(false)` synchronously inside `MealPlannerWidget`'s `startDrag()` the moment a `type:'new'` drag begins (not in the drop handler), and by having the `onOpenFullscreen` callback close the box before setting `openFile`. Since both card faces route "Drag to plan" through the same single `onStartDrag` prop (`RecipeStackCard` → `RecipeBoxModal` → `MealPlannerWidget.startDrag`), fixing it once in `startDrag` covers both — there's no separate per-face logic to duplicate the fix into. This also made the earlier "collapsed backdrop" mechanism (transparent, pointer-events:none, but still visible) dead code, since the modal is now always unmounted before that state could exist — removed rather than left as an unused prop/CSS class.

**`.cc2-mp-root` gets an explicit solid background — a deliberate, per-widget exception to the "every widget just shows the `.ws-shell` glass card through" convention every other `cc2-*` widget follows** — but the *token* took two passes to land correctly. First pass used `--cc2-bg` (matching the sticky day-header/slot-label/corner, which already needed an opaque background to occlude grid content scrolling underneath them) — this did unify the widget into one flat color, but that color reads as `--cc2-bg`'s actual role in this token system: the **recessed-pocket** tone (see `.cc2-kb-column`'s own comment: `.ws-shell` glass card → recessed `--cc2-bg` pocket → raised `--cc2-bg-raised` chip on top), one level darker than what any other widget's own outer surface actually shows — hence "too dark, doesn't match the rest of the cards" in dark mode especially (where `--cc2-glass-bg` is only ~5% opaque, so other widgets' apparent color sits close to `--cc2-bg-raised`, not `--cc2-bg`). Corrected to `--cc2-bg-raised` throughout the root/corner/day-header/slot-label — the same token `.cc2-recipe-fs-backdrop` uses for exactly this reason ("near-white ivory (`--cc2-bg-raised`), not the warm tan stage color (`--cc2-bg`)... matches the card-not-stage treatment"). Meal-block cards flipped the other way, from `--cc2-bg-raised` to `--cc2-bg`, to keep their contrast against the now-lighter root (mirroring `RecipeFullscreen`'s own backdrop-vs-inset-card relationship: raised backdrop, `--cc2-bg` inset card) — and `.cc2-mp-block-ctrl` (the hover duplicate/remove icon buttons sitting on top of a block) flipped from `--cc2-bg` to `--cc2-bg-raised` in turn, so it still contrasts against the now-darker block. If another widget ever needs this same "flat, not glass" treatment: use `--cc2-bg-raised` for the widget's own outer surface, not `--cc2-bg` — that token is for a nested recessed inset one level *inside* the card, not the card itself.

**"+ Blank" (`BlankMealModal.tsx`, new) — a way to plan a meal with no recipe note behind it (e.g. "Granola bars"), type-first rather than place-then-rename.** Considered placing a blank draggable placeholder first and renaming it in-place afterward, but placed meal blocks have no rename interaction anywhere in this widget today (click opens the recipe or starts a move-drag) — building one just for this would be new, speculative surface area. Typing the name first avoids that entirely: the modal (same shell as `RecipeImportModal` — one text input, Enter submits) captures the title, then hands it straight into the *already-existing* click-to-place flow (`startPlacing`, the same code path "Duplicate" uses) with zero new placement or editing code. No data-model change was needed either — `placeMeal` already just takes a plain title string. One minor accepted compromise: `startPlacing` needs a starting `x, y` for the ghost, but there's no real cursor position available when the modal is confirmed via Enter (only a `KeyboardEvent`) — it starts at the viewport center and snaps to the real pointer on the very next `pointermove`, so the placeholder position is only ever visible for a single frame.

**A block with no matching recipe file (`!block.recipePath`, both blank meals and a real recipe that's since been renamed/deleted) gets the exact same visual treatment as a normal block — full color bar, solid border, stretch/duplicate/remove all work identically.** An earlier version dimmed these (dashed border, faint bar/text) and disabled the stretch handle — the user explicitly asked to drop that: a blank item is still a real, deliberate meal plan entry, not a broken/degraded state, and should look and behave like one (including spanning multiple days). The only remaining difference is behavioral, not visual: `handleOpenBlock` shows `new Notice(\`No recipe found for "${block.recipeTitle}"\`)` (Obsidian's own toast, same pattern already used in `AIPanel.tsx`) instead of opening `RecipeFullscreen`, since there's genuinely no file to open. The `missing` boolean still exists in `MealBlockCard` — it now only drives that Notice and the hover tooltip text ("… (recipe not found)"), no longer a CSS class.

**Wired into the per-widget tone system, Trim only — deliberately no Wash on `.cc2-mp-root`.** This widget already carries the explicit solid-background exception documented above (a considered, structural choice, not an oversight), and combined with the per-slot block-bar colors below, a full background tint on top of both risked a cluttered result rather than adding anything — skipping Wash here is the restrained choice, not a limitation (contrast with the "Wash is the default expectation" framing under "Per-Widget Accent Color," where this is one of the few deliberate, structurally-justified holdouts). Elements following the widget-level `--t`: the "THIS WEEK" badge, the "+" glyphs in "+ Blank"/"+ Recipes", the hovered/hot day-cell highlight, a hovered block's border, a hot (drag-target) block's outline, and the stretch-handle grip. The floating drag ghost and "Drop on a planner slot ↓" hint — portaled straight to `document.body`, previously on Obsidian's raw globals only — also now read `--t` (falling back to the same `--interactive-accent` as before), which required extending the shared portal token-bridge selector list (`.cc2-mp-ghost, .cc2-mp-drop-hint` alongside `.cc2-cal-fs-backdrop`/etc.) so `--cc2-tone-*` actually exists in that portal's scope. `.cc2-mp-box-search`'s focus ring stays plain `--cc2-accent` — a focus ring, not a brand moment, matching every other search input in the app.

**Per-slot color (Breakfast/Snacks/Lunch/Dinner) for the meal-block's left bar — a new, separate feature from the widget-level tone above, capped at these 4 fixed slots so it can't become an unbounded rainbow.** A small swatch-dot button (`.cc2-mp-slot-color-btn`) sits beside each row label (`MealSlotLabel`, new component in `MealPlannerWidget.tsx`) and opens the shared `TonePickerPopover` with `showWash={false}` — a slot is just scattered 3px bars, not a surface to wash. Stored as `config.slotColors: Record<string, { tone?: string }>` keyed by slot name, tone-only (no `wash` field — same reasoning). `MEAL_SLOTS` (`meal-plan.ts`) is a fixed 4-element array, so no `MealBlock` data-model change was needed. Written through `onConfigChange` (`WidgetProps`' widget-self-write capability — see "Per-Widget Accent Color" above — `MealPlannerWidget` now destructures both `config` and `onConfigChange`, previously ignored entirely).

`.cc2-mp-block-bar` reads the placed block's own `row` at render time → `MEAL_SLOTS[row]` → looks up `slotColors[name]?.tone`, applied per-instance via `data-tone` directly on that one `<span>` (not a static CSS selector, since the color varies per-block based on data). The trickier part: `--t` is an inherited CSS custom property, and `.cc2-mp-root` already sets its own `--t` from the widget-level tone above — without a fix, a block in a slot with **no** color chosen would silently inherit the widget-level tone through normal CSS cascade instead of showing the plain green fallback, breaking "every board looks exactly as it does today until someone opts a slot into a color." Fixed by setting an inline `style={{ '--t': 'initial' }}` on the bar span itself whenever its slot has no tone — `initial` resets a custom property to the CSS-spec "guaranteed-invalid value" at that element (and would cascade to descendants, but this span has none), which makes `var(--t, #5F9E6E)` fall through to the fallback exactly as if `--t` had never been set by anything above it. A block that gets **moved** to a different slot picks up the new slot's color for free on the next render — color is derived from `row` live, never cached per-block, so no drag-preview logic was needed for this to work correctly. The ghost bar and drag-in-progress pill deliberately stay on the widget-level tone/fallback, not slot-aware — a not-yet-placed drag has no known destination slot to preview.

## Recipe Box Widget (`cc2-rb-*`) — standalone sibling of the Meal Planner's Recipe Box

A second, independent way to browse recipes, sitting alongside (not replacing) the plain-list `RecipeVaultWidget` — the user wanted to try the Meal Planner's card-stack UI as its own widget without losing the fallback if they end up preferring the list. Registered as `'recipe-box'`, default and min both `6×5` (min raised from an initial `{w:4,h:3}` once the user saw how much headroom `6×5` actually gives the cards and asked to lock it in as the floor rather than let the widget go smaller and cramped).

**Shared math, separate everything else.** The one thing that had to stay byte-for-byte identical between the modal and the widget was the scroll-driven peel physics itself (`peelFor`) — not because the surrounding code is similar, but because the *exact numeric feel* was the whole point of reusing it. Extracted to `src/widgets/shared/peel-stack.ts` as a pure, parameterized function (`peelFor(i, k, cfg: PeelConfig)`, `cfg = {peek, scaleStep, cap, front}`) — both `RecipeBoxModal.tsx` and `RecipeBoxWidget.tsx` import it and pass their own tuned config (the modal keeps its fixed `{peek:15, scaleStep:0.055, cap:3, front:45}`; the widget's config is computed live — see Sizing below). Everything else — the scroll handler, DOM refs, the `front-1..front+5` mount window, the card markup — stays independently implemented in each file; this is `src/widgets/shared/`'s first file, and the bar for adding to it should stay this high (exact-behavior math only, not "similar-looking JSX").

**What's deliberately missing vs. the modal, per explicit request:** no flip (the card only ever shows its front — no `flipped` state, no back face, no `backface-visibility`/`preserve-3d` CSS at all), no "Drag to plan" (this widget never places meals — no pointer-drag wiring, no ties into `meal-plan.ts`). Clicking anywhere on a card opens `RecipeFullscreen` directly (`onOpen` prop on `RecipeStackCardCompact`), replacing both the removed flip-to-see-details and the removed "Full recipe →" button with one action. **Create/"Add with AI" ARE present here** (unlike an earlier browse-only draft) — the user wants this widget to be a genuine alternative front end for the vault, not just a viewer, so both buttons and modals (`RecipeCreateModal`, `RecipeImportModal`) are wired in identically to `RecipeVaultWidget`.

**`useRecipeImport()` (`recipe-vault/useRecipeImport.ts`, new) — extracted the instant a second caller needed the exact same AI-import flow.** Unlike most "wait for a third instance" cases in this codebase, the YOLO-scoping + `forceNewConversation` handoff is real, previously-debugged behavior (see the `stdin.end()` and stale-closure notes elsewhere in this doc) — copy-pasting it into `RecipeBoxWidget` risked silently reintroducing a subtly different, broken variant instead of reusing the one proven-correct version, so this one was worth extracting at two call sites rather than waiting for a third. The hook returns `{settings, canImportWithAI, isDark, handleImport}`; it deliberately does **not** own `showImport`/`setShowImport` — that stays local to each widget (`onImport={url => { setShowImport(false); void handleImport(url); }}`), since modal-visibility is UI state specific to each caller, not shared behavior.

**Sizing is measured, not fixed.** An earlier pass hardcoded scaled-down constants (roughly half the modal's numbers) — this looked fine at first but left dead space at the widget's actual default size and would've looked wrong again the next time it was resized, the same underlying bug already fixed once in `RecipeBoxModal` (see the "modal too long" note above: a `flex:1` area sized to something other than what it actually needs). Fixed properly this time with a `ResizeObserver` on the scrollable stack container (`RecipeBoxWidget.tsx`): card width/height, top offset, and the derived `PeelConfig` (`peek`, `front`) are all computed from the *measured* stack area on every layout change, using the same proportions the modal's fixed layout has (stage 370 / top 16 / front 45 / card 296 / cardStep 236 / trackPad 200 → e.g. `cardHeight = stackHeight * 0.80`, `topOffset = stackHeight * 0.043`, etc.) rather than one frozen pixel target. This is a genuinely different technique from the container-query pattern used elsewhere (Task Manager's row→column stack) — container queries only toggle discrete CSS rules at breakpoints, they can't continuously drive a JS-side physics constant, so `ResizeObserver` + computed inline styles is the right tool specifically when a *value*, not a *layout mode*, needs to track the widget's live size. `scaleStep` (0.055) stays fixed — it's a ratio, not a pixel value, so it doesn't need scaling. The practical upshot: since min size is now `6×5`, cards render close to the modal's own original size at the default/minimum, and only get larger if the widget is resized up — no fixed "de-facto max size" baked in.

**Deliberately NOT wired into the per-widget tone system, per explicit request — the card face itself stays untouched.** `RecipeBoxWidget`'s Widget Settings modal still offers the swatch picker (`showWash={false}` — see `RecipeFullscreen`'s note above for why), but purely so it has somewhere to live for the fullscreen view it opens; nothing on the card-stack UI itself reads `--t`. The card face is photo-dominated (a recipe's real image, or a solid fallback color when there's none), and the existing category-chip treatment is deliberately translucent-white specifically so it stays legible over *any* photo — tinting it risks reintroducing a readability problem already solved once. `.cc2-rb-root` still gets `data-tone`/`data-wash` set (from `config.tone`/`config.wash`, the standard read), but purely to *forward* those values into `RecipeFullscreen` when it opens (`<RecipeFullscreen tone={tone} wash={wash} />`) — mirroring exactly how Calendar's compact widget passes its own tone down into `CalendarFullscreen`. No CSS in this widget's own stylesheet consumes `--t` at all.

## Navigation

The topbar is a **floating glass capsule** — not a full-width strip, and (as of the Programa-inspired pass) a genuine overlay rather than a flow element. It floats 10px from the stage edges with `margin: 10px 10px 0`, `border-radius: 16px`, and a warm drop shadow.

```
Height:        46px
Border-radius: 16px
Margin:        10px 10px 0   ← creates the float gap
Padding:       0 14px 0 10px
Background:    var(--cc2-glass-bg) + backdrop-filter (light mode: rgba(254,251,246,0.82) — genuinely translucent, not near-opaque)
Border:        1px solid var(--cc2-border-mid)
Shadow (light): 0 4px 24px rgba(30,24,16,0.14), 0 1px 5px rgba(30,24,16,0.08), inset highlight
Position:      absolute; top/left/right: 0 — layered over the grid, z-index 20
```

**True floating, not just visually styled to look floating:** `.cc2-topbar` and `.cc2-edit-banner` are `position: absolute` over `.cc2-stage`, and `.cc2-grid-wrapper` is `position: absolute; inset: 0` instead of being a flex sibling below the topbar. `--cc2-topbar-h` (56px = 10px margin + 46px height) is defined once on `.cc2-stage` and reused for the edit banner's `top` offset. This means scrolled widget content actually passes underneath/behind the translucent, blurred capsule as you scroll — it doesn't stop dead at the topbar's lower edge.

**Top clearance is a grid row, not CSS padding.** The first version of this used `padding-top: calc(var(--cc2-topbar-h) + Npx)` on `.cc2-grid-wrapper` — that reserved visual space but nothing stopped a widget actually being dragged/placed under the nav; it was a cosmetic offset, not a real constraint. `GridPage.tsx` now renders a locked, non-persisted `grid-stack-item` (`gs-id="__nav-spacer__"`) as the first child of `.grid-stack`, spanning the full 12-column width at row 0, `gs-h="1"`. GridStack's engine treats it as a real occupied node: `autoPosition` on new widgets skips it, and (with `float:false`) nothing can be dragged onto it since it's `gs-locked`/`gs-no-move`/`gs-no-resize`. It's invisible (`.cc2-grid-spacer` has `pointer-events:none` and no background) and deliberately excluded from `page.items`, so it's never part of a page's saved layout, never shown in the Add Widget library, and never reaches `onLayoutChange`.

Because `cellHeight` is 80px and the topbar's actual footprint is only ~56px, a full reserved row is coarser than needed — `.cc2-grid-wrapper .grid-stack` has `margin-top: -18px` to visually trim the excess without touching the grid math (the spacer still logically occupies a full row for collision purposes; this only shifts where things render). If the gap still looks off, adjust this margin value first before touching the spacer's `gs-h`.

**Caveat:** any existing page with a widget already saved at row 0 will have it auto-pushed down by GridStack on next load to resolve the collision with the new locked spacer — a one-time, cosmetic shift, not data loss.

**Tabs:** Vertically centered (not stretch), `padding: 6px 16px`, `border-radius: 10px`, kept compact (no extra letter-spacing/whitespace added) — page add/remove is coming, so the tab strip needs to stay tight rather than sprawl. No underline. `.cc2-tab` is hand-guarded flush (see "Obsidian CSS Override Gotchas" — this is a `<button>`, and its base rule needs `background`/`border`/`box-shadow: none !important` or *every* tab shows Obsidian's default raised look, not just the inactive ones). Default active state (dark mode + fallback) = warm pill background `rgba(30,24,16,0.10)` + inset highlight + outer shadow. **Light mode active tab** is a translucent warm-white highlight — `rgba(255,253,248,0.55)` background + inset top highlight + a real outer drop shadow — low enough opacity that the blurred capsule/page content still bleeds through (the Programa "floats, slightly opaque" feel), while the outer shadow (not just an inset one) is what actually gives it lift over the flat, unselected tabs. Every property on `.active` that the base rule guards with `!important` needs `!important` here too, or the higher-specificity `.active` rule still loses (see gotcha #3).

**Pages vs. features split:** `.cc2-topbar-actions` (Edit, Add Widget, AI toggle) gets a `border-left: 1px solid var(--cc2-border)` + `padding-left: 12px` divider before it, separating primary navigation (page tabs, left) from secondary features (right) — the same split as Programa's nav-links / Sign-in divide.

**Edit toggle:** Flush like the AI toggle — flat SVG icon (pencil / checkmark, replacing the old Unicode `⊞`/`✓` glyphs) + label, no border/background/shadow at rest, hover-only tint. `<svg>` needs its own `width/height/min-width: 13px !important` rule (gotcha #2) — a raw `width="13"` attribute on the element isn't enough. When edit mode is actually on, it keeps a solid amber fill (`.cc2-edit-toggle.active`) — that's a functional state signal (you're in a mode that can break your layout), not leftover "raised button" chrome, so it stays exempt from the flush look while active.

**Add Widget** stays a boxed physical key button (embossed, `.cc2-add-widget-btn`) — it's the one primary, stand-out CTA in the action cluster, only shown in edit mode, deliberately exempt from the flush rollout.

**AI toggle button** (`.cc2-ai-toggle-btn`) uses `.cc2-flush-btn` — flat provider logo, no chrome, opacity dims to 0.8 at rest and 1.0 on hover/active.

This is a first pass on the translucency/highlight values (0.82 capsule opacity, 0.55 active-tab opacity, -18px grid trim) — tune by eye once it's visible live; there was no way to verify the exact Programa color/opacity/spacing values from static analysis, only the structural pattern (true overlay, subtle highlight, compact tabs, secondary-action divider, reserved-not-padded top row).

**Grid wrapper:** `padding: 6px 10px 10px` — the 10px side padding aligns widget columns with the nav capsule edges. (Top clearance for the nav itself comes from the spacer row above, not this padding.)

**Event colors (the 11-swatch picker in the Add/Edit Event modal, and every already-created event's rendered dot/chip/border) are remapped to the plugin's own 10-tone palette, not Google's raw Material colors** (`CC_EVENT_COLORS` in `calendar.ts`). Matched by hue/character rather than list position — Tomato→Rust, Flamingo→Rose, Tangerine→Terracotta, Banana→Ochre, Sage→Sage (literal name match), Basil→Moss, Peacock→Spruce, Blueberry→Indigo, Lavender→Slate, Grape→Plum — with **Graphite (id 8) deliberately left unmapped**, kept as Google's own neutral gray (`#888888`) rather than forced onto one of our 10 hues, since a "no strong color" option should stay actually neutral. **Don't use `var(--cc2-accent)` / `var(--interactive-accent)` for small text.** It's Obsidian's user-configurable accent color — on some vault themes it's light/pale enough to wash out at small sizes (bit us on the "Default" color-swatch button's active-state text). Prefer `var(--cc2-text)` for anything under ~12px that needs to read as "selected," and reserve the accent color for larger UI or deliberate "color pop" moments (e.g. the active nav tab's text tint, which mixes accent at 40% into `--cc2-text` rather than using it at full strength).

**Toggle switches need real track/thumb contrast.** `.cc2-cal-toggle`'s off-state track originally used `--cc2-btn-bg` (5.5%/6% tint) against a near-white/near-black thumb — barely any differentiation in light mode. Use `--cc2-btn-border` (stronger tint) for an unchecked toggle track, not `--cc2-btn-bg`. Also: pair the toggle with its label inside one `gap`-based flex row with a shared `onClick` (see `.cc2-cal-field-row` in `CalendarStripWidget.tsx`) rather than `justify-content: space-between` — spreading a label and its control to opposite ends of a wide row makes the relationship between them unclear.

## Kanban Board Widget

`cc2-kb-*`. Shares its data source (`todos.ts`) with Task Manager — same TODO file, same bucket concept, same `cc2-active-buckets` frontmatter list — this widget is the multi-column board view over that data, Task Manager is the single-active-task focus view over a filtered slice of it (only buckets in `activeBucketNames`).

**No board-wide color control in the Widget Settings modal — per-bucket color (below) replaced it entirely, rather than offering two overlapping color pickers.** `config.tone`/`config.wash` still exist as fields (nothing reads them at the board level anymore) and `WidgetSettingsModal.tsx` skips rendering `TonePicker` for `type === 'kanban'` specifically (every other widget still gets it) — `confirm()` also skips writing `patch.tone`/`patch.wash` for Kanban, so saving other settings (board/file, bucket Task-Manager toggles) never silently resets a value nothing lets you see or change anymore.

**Per-bucket color — the swatch-dot button in each column header (`.cc2-kb-column-color-btn`, showing that bucket's current tone as a live preview, `--cc2-faint` when unset).** Clicking it opens `TonePickerPopover` (`src/widgets/shared/TonePickerPopover.tsx`) — a small floating panel (portaled to `<body>`, since `.cc2-kb-column`/`.cc2-kb-board` both clip with `overflow: hidden` and would cut off an anchored-in-place popover; positioned from the trigger's own `getBoundingClientRect()`, not CSS anchoring) containing the same `TonePicker` component the settings modal uses elsewhere. Originally a private `BucketColorPopover` inside `KanbanWidget.tsx`; extracted into the shared, generalized component (parameterized by `tone`/`wash`/`onToneChange`/`onWashChange`/`onClose`/`showWash`) the moment Meal Planner's per-slot picker (see its own section) needed the identical portal-and-position shell — Kanban's own call site is now just a thin pass of its bucket-specific props into the shared component. Deliberately kept out of the Widget Settings modal, per explicit request — a board with many buckets would turn "pick a color" into a long scrolling list; a contextual per-column control scales however many buckets exist without bloating the shared settings screen.

Stored in `config.bucketColors: Record<string, { tone?: string; wash?: boolean }>`, keyed by bucket name. An unset bucket renders as plain Paper/Trim — the same "default is invisible until touched" rule the whole tone feature follows elsewhere. Column title (`.cc2-kb-column-name`) and the column's own background/border (`.cc2-kb-column[data-wash]`, layered onto the existing `--cc2-bg` pocket rather than replacing it) both follow the bucket's own `--t`.

**The "TM" badge (`.cc2-kb-tm-badge`) was removed outright, not just restyled — an explicit request, not a bug fix.** It was already hardcoded to `var(--cc2-accent)` (a real leak, same pattern as Calendar's), but rather than fixing its color the badge itself was deleted (along with the now-dead `isActive` prop threading and the parent's `activeSet` computation) once the Widget Settings modal's own bucket-list section (below) made "is this bucket in Task Manager" a proper setting instead of needing a constant visual reminder on every column.

**Header layout — freeing up room for the title was two separate fixes, not one.** The header used to carry a *second*, redundant `<span style={{flex:1}}/>` spacer alongside `.cc2-kb-column-name`'s own `flex: 1` — with two flex:1 elements splitting the same remaining space 50/50, the title only ever got half of what was actually available, truncating far earlier than the real available room justified. Removed the redundant spacer entirely (the title's own `flex: 1` is enough to push everything after it to the far edge) and added `min-width: 0` alongside it (the classic flexbox gotcha: a flex item won't shrink below its content's intrinsic width without this, regardless of `overflow: hidden`/`text-overflow: ellipsis` being set). Header order is now: color-dot → title (all remaining space) → delete button → "{n} TODO" count → add-task button — count deliberately sits beside the `+` rather than immediately after the title, so the whole right-hand icon/count cluster reads as one group, away from the title entirely.

**The Widget Settings modal's file/folder picker only chooses *which* TODO file/board — which buckets feed Task Manager's active pool is a separate, per-bucket decision, surfaced as its own section** (`KanbanBucketSection` in `WidgetSettingsModal.tsx`) between the file picker and the color section. Unlike `tone`/`wash`/`listFile`/`boardName`/`bucketColors` (all per-widget `config`, only written when the modal's Save/Add button is clicked, or — for `bucketColors` — the moment a per-bucket swatch is picked via the popover above), each bucket's Task-Manager membership is a property of the **shared TODO file's own frontmatter** — the exact same `cc2-active-buckets` list `AddBucketModal`'s "include in Task Manager" checkbox already writes at bucket-creation time. So this section writes immediately the instant a toggle is flipped (`setBucketActive` in `todos.ts`, a new function — same frontmatter add/remove `addBucket`/`deleteBucket` already do, just callable for a bucket that already exists, not only at creation), independent of whether the user ever clicks this modal's own Save button. The section reads whichever file the modal's *own* picker currently resolves to (`effectiveListFile`, derived from `fileMode`/`selected`/`newName` — not `existingConfig.listFile`), so switching the picker to a different existing board updates the bucket list live within the same modal session.

## Meeting Log Widget

`cc2-mtg-*`. Simple list view over `meetings.ts` — no file-setup section in its Widget Settings modal (no folder/board to pick), so that modal is just the color picker for this widget.

**Wired into the per-widget tone system, Trim + Wash both.** Trim elements following `--t`: the row date (`.cc2-mtg-row-date`) and the attendee "tag" chip's text (`.cc2-mtg-row-tag` — shown when a meeting's frontmatter has a non-empty `attendees` value; only the text color changes, not its background/border chip styling, keeping the visual footprint small). Wash tints `.cc2-mtg-root` itself — same recipe as Calendar's (`background: linear-gradient(var(--t-bg), var(--t-bg)), var(--cc2-bg-raised); border-color: var(--t-line)`), with a `border: 1px solid transparent` on the base rule so the border-color transition doesn't pop in/shift layout when toggled. (An earlier pass wired this Trim-only on a misread of "keep it subtle" as "no Wash" — corrected; the request was about which *elements* get color, not about withholding Wash.)

## Grocery List Widget — frictionless entry pattern

`cc2-lst-*`. Visually it's mostly borrowed wholesale from Kanban (`.cc2-kb-check`, `.cc2-kb-card-delete`, `.cc2-kb-add-row` recipes, copied rather than shared via class name since the two widgets' markup shapes differ slightly) — the one deliberate departure is the **add-row never closes**. Kanban's "add task" row is a toggled affordance (click + → row appears → commit closes it again); Grocery List's input is permanently mounted, and committing an item (Enter) clears it and immediately re-focuses it rather than closing anything. This is intentional, not an oversight — grocery/ingredient entry is rapid, one-item-after-another, and a click-to-reopen step between every item breaks that flow. If a future widget has a similar "fast repeated entry" need, reuse this pattern (`autoFocus` + refocus-after-commit) rather than Kanban's toggle-row.

Ingredient/item text is a single free-typed line (e.g. `2 lbs chicken breast`), parsed into `{qty, unit, name}` by `src/data-sources/ingredient-line.ts`'s `parseIngredientLine` — a leading-number-plus-known-unit-word regex, not a form with separate fields. This util is shared with the (future) Recipe Vault so both widgets treat "ingredient" as the same shape. Storage is still just a plain `- [ ] <raw text>` checkbox line (mirrors `todos.ts`'s philosophy) — the qty/unit/name split is derived on read, never forced into frontmatter/YAML.

**Wired into the per-widget tone system, Trim + Wash both — same shape as Meeting Log.** Wash tints `.cc2-lst-root` itself (identical recipe: `background: linear-gradient(var(--t-bg), var(--t-bg)), var(--cc2-bg-raised); border-color: var(--t-line);`, with `border: 1px solid transparent` on the base rule so toggling it doesn't pop/shift layout). Trim elements following `--t`: the checked-item checkbox fill (`.cc2-lst-check` in its `.done` state — same `var(--t, #5F9E6E)` fallback-preserving divergence as `RecipeFullscreen`'s checkbox, for the same reason: falls back to the shared green everyone already sees, only diverges once a tone is actively chosen) and the "Clear checked" button text (`.cc2-lst-clear-btn`, both resting and hover color — it inherits `.cc2-flush-btn`'s plain muted/text colors otherwise, so this needed its own `!important`-guarded override per the Obsidian button-chrome gotcha).
